## §2. Кому рассылать протокол

После утверждения протокол получают участники встречи по календарю (по `meeting_uid`, иначе по названию и дню), исполнители новых задач и исполнители задач прошлого протокола, по которым на встрече что-то сказали. Руководитель письмо не получает, он утверждал протокол. Встреча не из календаря — только исполнители.

## §1. Сверка с прошлым протоколом

- Прошлый протокол — последний утверждённый протокол той же встречи (по названию), иначе последний утверждённый до неё.
- Модель получает задачи прошлого протокола с номерами и возвращает по каждой статус: «выполнена», «в работе», «перенесена», «изменилась» или «не обсуждали», новую формулировку и срок, цитату.
- Код проверяет: номер есть в прошлом протоколе; статус из списка; без подтверждённой цитаты статус становится «не обсуждали»; задача, о которой молчали, тоже получает «не обсуждали».
- Изменённые и перенесённые задачи показываются в протоколе как «было → стало ⚠️ согласуйте». В Telegram карточка начинается со строки «Изменились задачи прошлого протокола: N. Утверждая протокол, вы согласуете изменения».
- После утверждения статусы попадают в журнал (`task_update`), кабинет показывает новые формулировки и сроки.
- Вопросы аватара по прошлому протоколу: «что готово? Задача не поменялась?»
- Правка протокола руководителем сверку не теряет.

## §3. Порядок задач

- У задачи есть поле «после» (`after`): номера задач этого протокола, которые нужно сделать раньше. Ставится, только если это прозвучало. Ссылки вперёд, на себя и мусор отбрасываются, поэтому цикла не бывает.
- Если срок задачи раньше срока её предшественника, ставится флаг, а в «Нерешённые вопросы» добавляется вопрос руководителю.
- В протоколе: «(после 1, 2)» у задачи и строка «Порядок: Шаг 1: задачи 1, 2 — параллельно → Шаг 2: задача 3».
- Задача со статусом «ждёт задачи N» ждёт, пока предшественники не выполнены. Когда сверка на следующей встрече отметит их выполненными, исполнитель один раз получает письмо «Можно начинать: …» (шаблон `task_go`, правится в кабинете).
