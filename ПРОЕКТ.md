## 1. Что продаём заказчику

Заказчик хочет «клонировать себя»: снять рутину и сделать так, чтобы встречи заканчивались действиями. Отсюда формула продукта:

> Помощник забирает рутину общения и доводит решения встреч до исполнения. Делает сам, руководитель узнаёт итог и может отменить. Руководитель решает только то, что требует решения.

Боли и случаи жизни разобраны в [JTBD.md](JTBD.md). Мерим эффект тем, что видно в журнале: доля событий, закрытых без руководителя, минуты руководителя в день, доля писем без правок, поручения в срок и застрявшие.

## 2. Каналы

| Канал | Роль | Как подключаем |
|---|---|---|
| **Почта** (резервный Gmail Пита, заменяется на почту заказчика) | Внешние письма: партнёры, смежники, клиенты. Входящие и исходящие | IMAP: опрос раз в 30–60 с. SMTP: отправка. Настройки только в `.env` |
| **Telegram-бот** | 1) Пульт руководителя: дайджест сделанного, окно отмены писем наружу, очередь решений. 2) Входящие от команды. 3) Поручения и напоминания исполнителям | Long polling, без вебхука, поэтому nginx не трогаем |
| **Веб-экран на стенде** | Обзор для руководителя и жюри: события, дела со стадиями, журнал, стоимость | FastAPI на :8080 |

Ограничения Telegram, которые надо учесть заранее:
- Бот не может первым написать человеку, который его не запустил. Для демо команду моделируем **группой «Команда (демо)»**: бот пишет туда и отмечает исполнителя по имени. Личные сообщения получает только руководитель.
- С компьютера Пита Telegram API недоступен. Всё, что связано с ботом, проверяем на сервере.

## 3. Устройство

```
Почта (IMAP) ─┐
Telegram ─────┼─> Событие ─> Агент (цикл с инструментами) ─> Черновик / дело
Часы/сроки ───┘                                                │
                                                               v
                                              Проверки кода (правила)
                                                               │
                       ┌── рутина ─────────────> Отправка сразу ─────┐
                       ├── от имени руководителя > Окно отмены ──────┼─> Журнал, дайджест
                       └── нужно решение ──────> Очередь решений ────┘
```

- **Событие:** письмо, сообщение в Telegram, заметка после встречи, наступивший срок. Повторное событие с тем же источником (Message-ID письма, id сообщения) не обрабатывается дважды.
- **Агент:** модель в цикле до 8 шагов. На каждом шаге вызывает инструмент или сдаёт структурированный результат. Это отвечает критерию «Агентность»: агент сам решает, что посмотреть и что подготовить.
- **Проверки кода:** модель не отправляет напрямую. Код проверяет получателя, обещания, цитаты и сроки и выбирает путь: отправить сразу, через окно отмены или в очередь решений.
- **Дело:** поручение или переписка со стадией (`новое → ждёт руководителя → отправлено → ждём ответ → закрыто / застряло`) и сроком. Застрявшее дело всплывает у руководителя.

### Инструменты агента

| Инструмент | Что делает |
|---|---|
| `read_event` | Текст события, отправитель, канал, вложения в виде текста |
| `search_history` | Прошлая переписка и договорённости с человеком или по теме |
| `team_directory` | Кто есть кто: роль, зона ответственности, канал связи |
| `list_cases` | Открытые дела и сроки по человеку или теме |
| `knowledge_lookup` | Утверждённые ответы и регламенты для типовых вопросов |
| `propose_message` | Черновик: кому, канал, текст, ссылки на основания |
| `propose_tasks` | Поручения из заметки: кто, что, срок, цитата из заметки |
| `ask_manager` | Вопрос руководителю, когда фактов не хватает или источники расходятся |

### Правила в коде

1. **Цитата сверяется с источником.** Каждый факт и каждое поручение ссылаются на фрагмент источника. Если фрагмента нет, факт из сообщения убирается. Если без него сообщение теряет смысл, событие уходит в очередь решений.
2. **Получатель берётся из справочника и переписки.** Неизвестный адрес — очередь решений.
3. **Никаких обещаний сверх регламента.** Деньги, скидки, сроки и обязательства, которых нет в источниках, код не пропускает в автоотправку.
4. **Срок — дата в будущем.** «К пятнице» код переводит в дату, модель только находит слова. Если срок не назван, ставится срок по умолчанию из настроек, например 3 рабочих дня, и он виден в дайджесте.
5. **Путь отправки** — по таблице автономности (раздел 4).
6. **Лимит стоимости в сутки.** При превышении агент останавливается и пишет руководителю.

## 5. Сценарии-кандидаты

Выбор после ТЗ. **[решает Пит]** Предлагаю A как хребет, к нему B и C, если хватит времени. A закрывает боль заказчика, B даёт почту, C собирается из уже накопленных дел.

### A. Встреча → поручения → исполнение

1. После созвона руководитель пишет боту заметку текстом или голосом. Расшифровка голоса — вопрос открытый, см. раздел 9.
2. Агент выделяет решения и поручения: кто, что, к какому сроку, с цитатой из заметки. Сверяет людей со справочником, смотрит открытые дела, чтобы не дублировать.
3. Поручения сразу уходят исполнителям: внутренним в группу Telegram, смежникам письмом. Каждое поручение становится делом со сроком. Руководитель получает одну строку «разослано 4 поручения» и список. Письма внешним партнёрам идут через окно отмены.
4. Перед сроком исполнителю приходит напоминание. Ответ «сделано» закрывает дело. Молчание после срока — сигнал руководителю «застряло».

### B. Разбор входящих

1. Письмо или сообщение приходит в почту или Telegram.
2. Агент определяет тип: типовой вопрос / нужно решение руководителя / статус / запрос смежнику / не требует действий. Определяет срочность.
3. На типовой вопрос готовит ответ из утверждённых материалов. Где нужно решение, готовит руководителю сводку на три строки и варианты. Запрос смежнику превращается в дело.
4. Дальше — по таблице автономности.

### C. Еженедельный апдейт команде

По расписанию агент собирает апдейт из дел за неделю: что закрыто, что застряло, приоритеты. Каждая строка ссылается на дело. Апдейт уходит в группу команды сам, руководитель видит его в дайджесте. Это сценарий из README, только факты для него берутся из журнала A и B, а не вводятся отдельно.

## 6. Стиль руководителя

- **Образцы:** 5–10 писем руководителя из материалов ТЗ подаются модели как примеры. Если образцов в ТЗ не будет, их пишет Пит.
- **Память правок:** когда руководитель правит черновик, пара «было → стало» сохраняется. В следующий раз похожие правки подаются как примеры. Приём из «Рисков в договоре».
- **Метрика:** доля черновиков, принятых без правок, и объём правки по дням прогона. Рост первой цифры показывает, что помощник учится стилю. Ответ на вопрос 4 из правила 10.

## 7. Данные (SQLite)

| Таблица | Что хранит |
|---|---|
| `people` | Справочник команды и смежников: имя, роль, зона, канал, адрес |
| `events` | Входящие события: канал, внешний id для защиты от повтора, текст, время |
| `cases` | Дела: тема, исполнитель, срок, стадия, связь с событием |
| `drafts` | Черновики: текст, основания с цитатами, статус проверок |
| `decisions` | Решение руководителя: согласен, правит или отклоняет, итоговый текст, время, сколько секунд думал |
| `outbox` | Что и куда отправлено, внешний id отправки |
| `style_edits` | Пары «было → стало» |
| `llm_calls` | Модель, токены на вход и выход, стоимость, длительность, к какому событию относится |

Учебные данные: вымышленный отдел онлайн-продаж, 6–8 человек, 2–3 смежника, 1–2 партнёра. Если ТЗ даст свои данные, берём их. Эталоны лежат отдельно от того, что видит агент.

## 8. Модели и стоимость

- **Сменный слой модели:** один интерфейс и провайдеры за ним. Сейчас есть DeepSeek (ключ работает, $10 на балансе) и Anthropic (ключ из клининга). Если ТЗ запретит внешние модели, добавляется GigaChat или YandexGPT без правки агента.
- **Стоимость одного запроса** считается из `llm_calls` по реальному прогону. Её же переносим в шаблон организатора. Плюс пересчёт на месяц: число событий в неделю × стоимость события + стенд.
